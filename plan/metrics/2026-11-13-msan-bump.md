## Item 2: 18 msan tests hit ctest's fixed 10 s

Where the numbers live
- The limit: `ctest/ctest.c` `TIMEOUT_S = 10` ("fixed; deliberately not configurable by a test file"), one wall timeout per test child,
  the same in every mode. `LIM_CPU_CHILD_S = 20` (RLIMIT_CPU, "twice the wall timeout") sits next to it and would also need to move
  if the wall limit does. `ctest/traps.c` has its own 3 s per expression, inside the same 10 s.
- The msan options: compile `-O1 -g -fsanitize=memory -fsanitize-memory-track-origins=2` in `rules/c.bzl` (`_MSAN`, used by
  `_COMPILE_BY_MODE` and `_LINK_BY_MODE`) and the same constant again in `rules/third_party.bzl:105` (mbedtls and `tls_peer` are
  instrumented with it). Runtime `MSAN_OPTIONS` is in `rules/ctest.bzl` `MSAN_ENV_LINES` (no `track_origins` there: origin tracking is a
  compile-time choice, the runtime option only has to not contradict it). `docs/toolchain.md` states level 2 as a design fact.

Measurement (what I could and could not do)
- The 18 business-apps tests are not in this repo and I may not build inside another lane's worktree. I measured a stand-in that
  stresses what origin tracking costs (loads and stores of memory with shadow propagation): a 64K random walk plus 4 KiB block
  memcpy/rotate/xor rounds, one test, `--no-remote-cache`, RE, `-O1` for msan. The target was a scratch `c_test` in `examples/hello`
  (deleted, not committed); the time is the test's own `clock_gettime`, reported through a deliberately failing check.
  The flag was changed by editing `_MSAN` in `rules/c.bzl` for the run and reverted (`git checkout rules/c.bzl`).

| Build | Test ms | vs release |
|---|---:|---:|
| release (`-O2`) | 58 | 1.0x |
| msan, track-origins=0 | 119 | 2.1x |
| msan, track-origins=1 | 169 | 2.9x |
| msan, track-origins=2 (today) | 283 (285 on a repeat) | 4.9x |

- Level 2 costs 1.7x over level 1 and 2.4x over level 0 on this load. One workload, one repeat of level 2 only: the ratios are
  indicative. This is NOT a measurement of mbedtls handshakes (crypto is heavier on shadow propagation than this loop), and I do not
  know the release time of the 18 tests. So the hypothesis of the product note (origin level 2 is what pushes them over 10 s) is
  consistent with the numbers but not proven: if a TLS test needs about 5 s in release, level 2 gives roughly 25 s and level 1
  about 15 s, and **level 1 alone would not be enough**; level 0 would be about 10 s, on the line.
- To settle it: a lane with access to `lib/io/tls_stream` runs `split_test_results` in msan at levels 2/1/0 (one `_MSAN` edit each)
  and records the time per test in the same way (release too). That is a measurement target in the product repo, not here.

Options and their rigor cost
1. **Per-mode wall timeout in ctest, a sealed constant** (e.g. 10 s release/san/tsan, 30 s msan; `LIM_CPU_CHILD_S` scaled the same;
   mode passed as a sealed define of the msan `ctest` build, never from a test file). Rigor cost: none on detection, msan finds
   exactly the same bugs; it only lets slow-but-correct tests finish. The risk is a real hang under msan waiting 30 s: bounded and
   harmless. The 10 s release limit, which is the one that keeps tests fast in the mutants/release path, is untouched. Needs
   `docs/ctest.md` and a canary that a hang still fails in msan (the existing timeout canary run in msan mode).
2. **Lower origin tracking to 1** (`_MSAN` in `c.bzl` and `third_party.bzl`, `docs/toolchain.md` and the T125/P003 text). Rigor cost:
   the detection of uninitialised use is unchanged (origins only enrich the report: level 1 reports the allocation or the stack
   variable that created the value, level 2 adds the chain of stores it travelled through). Reports get less informative, so
   triage is slower, not weaker. About 1.7x faster on the stand-in; may not suffice alone (above).
3. **Level 0**: about 2.4x faster, detection unchanged, but reports say "uninitialized value" with no origin; with halt_on_error a
   report with no origin is hard to act on for agent lanes. Not recommended unless 1 plus option 1 is not enough.
4. **Product splits or cuts** (fewer iterations, 2^16 -> smaller capacity): the product note is right that this weakens coverage or
   needs new `expected-tests.json` ids. Not recommended for gate-induced slowness.
5. **Per-test opt-out of msan** (a signed list): weakest, loses msan on the crypto paths, which are where uninitialised-read bugs
   hurt most. Rejected.

Recommendation: option 1 (per-mode sealed timeout, msan x3, CPU rlimit scaled), keep level 2. It is the only option that removes
the problem independent of the measurement, costs no detection and no report quality. Add option 2 only if the TLS measurement shows
that even 30 s is tight (more than about 12 s at level 2 means the farm cost of the msan run itself is the next problem). Owner
decision, because the timeout is a sealed gate constant.

## Item 3: `osal_real_test` and the sanitizer stack minimum

Fact (from the product note): the test starts a real thread on a caller-supplied stack of `OSAL_STACK_MIN + OSAL_STACK_RESERVE + 16`
bytes on purpose (it tests the minimum). The msan and tsan runtimes intercept `pthread_create` and refuse a stack smaller than their
own per-thread need ("pre-allocated stack size is insufficient: 16384 < 137280"). `threads = True` is required by the gate (`threads-undeclared`
otherwise), which gives the test a tsan results target; msan covers every test. So the test cannot pass under tsan and msan as written.
A `#if __has_feature(...)` branch in the test is a forbidden suppression (AGENTS.md rule 2).

Options
- **A. Gate-sealed per-mode exemption.** The gate (not the product) holds a sealed list "tests that run only in modes X", keyed by
  module label, e.g. in `policy/` signed by the owner. `tests-msan`/`tests-tsan` drop its ids from their expected sets and report an
  info finding `sanitizer-exempt`. Cost: a hole by construction, one more list to maintain per product, keyed by name, so a product can
  ask for the same exemption for any test; the gate must verify the label still exists and that the exemption has a reason; the
  signed key holder is the owner.
- **B. Product-declared sanitizer-incompatible test with signed approval.** `c_test(..., sanitizer_incompatible = "tsan,msan")` plus a
  signed approval record (existing approvals mechanism, `gate/tests/test_approvals*.py`) that names the test and carries a reason.
  The gate's expected sets drop the test only when the approval verifies. Cost: new rule attribute and approval kind, but exemptions
  are visible in the product diff, expire or are revoked like other approvals, and the owner signs each. Equivalent in effect to A
  with better ownership and review, and consistent with how the gate already treats loosenings.
- **C. Product split.** The minimum-stack check does not need a real thread for everything: split `osal_real_test` into (1) the stack
  arithmetic and refusal paths (`OSAL_STACK_MIN` accepted, one byte less rejected) without a thread, which runs in every mode, and
  (2) the single real-thread start on the exact minimum stack, which is the claim that no sanitizer can run. C alone leaves (2)
  failing under msan/tsan, so C only shrinks what A or B must exempt. New test ids need `expected-tests.json` entries.
- **D. A sanitizer-sized stack constant in osal** (product): changes the product behaviour under test; no, it tests a different thing.

Recommendation: B, with C applied first so the exempt test is as small as possible (the minimum-stack thread start and nothing else).
B keeps the gate's rule that nothing is exempt without an owner-signed, reviewed record, and avoids A's gate-side name list. If the
owner wants no new gate attribute, A with the same signing is acceptable but worse. Decision for the owner either way; do not implement
before then, and msan/tsan results of every other test stay required.
