# R011: design a gate-held performance check (`perf` gate, B13)

Repo: `Mivr/c-rigor-gate` (read-only for you). Design research for the orchestrator. No code changes in any repo.
Scratch dir: `/var/tmp/cache/R011` (rw). You may build and run small probes there with the gate's hermetic
toolchain through Buck2 (the RE farm), for example to measure timing noise.

## Context
- B13: parser paths that are quadratic in the input, bounded today only by input caps (annas-c: json duplicate
  keys, http dot-segment removal; fixed by A021/A026, but nothing stops a regression). Unit tests check results, not
  cost. A test-author or implementer agent can ship an O(n^2) path that passes every gate.
- The gate already holds hidden material for grading: the witness bundle (`docs/witness.md`, P002, T037/T039), passed
  as `--witness DIR`, bound by sha256 in the verdict and never shown to agents. A perf check should be hidden the same
  way, so it cannot be tuned against.
- Builds and test runs happen on a shared NativeLink RE farm. Wall time there is noisy (shared load, different
  workers), and results are cached by action key.
- Read: `docs/grade.md` (gates, order, verdict, `--uncached`), `docs/witness.md`, `rules/c.bzl` (`c_test`, the
  `results.jsonl` runner), `ctest/`, `docs/mutate.md` ("Timeouts"), and `plan/backlog.d/B13.md`.

## Deliverable (final message, text, under 1,500 words)
1. **Measurement options, ranked:**
   - (a) wall-time scaling ratios (time at n and k*n, pass if the ratio stays under a bound), repeated, median, with the
     noise you **measure** on the farm in a small probe (report it);
   - (b) deterministic operation counts: instructions via a counter the toolchain already has, or counts through the
     product's own port seams (allocator calls, bytes touched), or a counting build mode;
   - (c) anything better.
   For each: determinism, flake rate, cost per grade, cacheability, and how an implementer could game it.
2. **The hidden test format:** what a perf test is (inputs generated by a gate-held generator at sizes n and k*n, a
   target function through the public header, a complexity class or budget), where it lives (beside the witness, or
   its own bundle), and how it binds into the verdict.
3. **Gate semantics:** gate name, place in `order.txt`, findings (names, severity per level), not-run rules, and the
   L-levels where it is required.
4. **Calibration plan on annas-c:** which functions (json objects with many keys, http paths with many dot segments,
   url, chunked bodies), and how to prove that it fails on the pre-A021/A026 quadratic versions (git history) and
   passes on main.
5. **A canary design** (a product with a planted quadratic path that every other gate passes), and a task breakdown
   of at most 4 implementation tasks with allowed paths.
